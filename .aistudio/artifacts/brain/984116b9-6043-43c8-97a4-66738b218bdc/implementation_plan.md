# แผนยกระดับความเสถียรฐานข้อมูลและแก้ไขปัญหาข้อมูลหายเมื่อเปิดใช้งานซ้ำ (Zero Data Loss & Persistence Hardening Plan)

เอกสารนี้สรุปผลการวิเคราะห์สาเหตุเชิงลึกของปัญหา **"เมื่อเช้าเปิดมาข้อมูลมาครบ แต่พอทิ้งไว้สักพักแล้วเปิดใหม่ข้อมูลหาย"** พร้อมแผนการแก้ไขถาวรเพื่อให้ระบบฐานข้อมูลมีความเสถียรสูงสุด 100%

---

## User Review & Critical Decisions

> [!IMPORTANT]
> **สรุป 3 สาเหตุหลักที่ทำให้เปิดตอนเช้าข้อมูลครบ แต่พอทิ้งไว้สักพักแล้วเปิดใหม่ข้อมูลหาย:**
> 1. **การลบคีย์อัตโนมัติระหว่างจัดเรียงตะกร้าข้อมูล (`deleteField` ใน `misplacedByShard`):** เมื่อเปิดหน้าเว็บครั้งแรก ระบบดึงข้อมูลจากทุก Shard มาแสดงจนครบ แต่ขณะเปิดหน้าเว็บทิ้งไว้ ระบบเบื้องหลัง (`migrateLegacyReportsToBundlesOnce`) จะพยายามย้ายรายงานจากตะกร้าเดิม (`Shard 0–9`) ไปยังตะกร้าใหม่ (`Shard 10–23`) แล้วสั่ง `deleteField()` ลบข้อมูลในตะกร้าเดิมทันที หากจังหวะนั้นโควตาการเขียนเต็ม หรือมีการเปิดเว็บเวอร์ชันเก่าควบคู่กัน ข้อมูลในตะกร้าเดิมจะถูกลบออกโดยที่ตะกร้าใหม่ยังไม่ได้บันทึก ทำให้พอเปิดใหม่ข้อมูลจึงหายไป
> 2. **พื้นที่แคชสำรองในเบราว์เซอร์เต็ม (`localStorage` 5MB Limit) ร่วมกับโควตาอ่าน Cloud Firestore:** เบราว์เซอร์จำกัดความจุ `localStorage` ไว้ที่ 5MB (ประมาณ 2.5 ล้านตัวอักษรภาษาไทย) แต่เดิมระบบบันทึกแคชซ้ำ 2 ชุด (`reports` และ `reports_backup`) ทำให้เมื่อข้อมูลสะสมมากขึ้น การบันทึกแคชลงเครื่องล้มเหลว เมื่อเปิดเว็บทิ้งไว้จนโควตาอ่านฟรีรายวันของ Firestore เต็ม พอเปิดหน้าเว็บใหม่จึงดึงข้อมูลไม่ได้ทั้งจาก Cloud และจากเครื่อง
> 3. **การสลับตัวกรองวันที่อัตโนมัติของหน้าแดชบอร์ด (`Auto-Date Switch`):** ตอนเช้าตรู่ที่ยังไม่มีจังหวัดใดส่งรายงานของวันนี้ หน้าแดชบอร์ดจะแสดงข้อมูลของ **"เมื่อวาน"** (ที่มีข้อมูลครบทุกจังหวัด) โดยอัตโนมัติ แต่พอทิ้งไว้สักพักแล้วมีจังหวัดแรกเริ่มส่งรายงานของ **"วันนี้"** เข้ามา พอเปิดเว็บใหม่ระบบจะสลับไปกรองเฉพาะ **"วันนี้"** (ซึ่งเพิ่งส่งมาไม่กี่แห่ง) ทำให้ดูเหมือนข้อมูลทั้งหมดหายไป

- **แนวทางหลักที่เลือกดำเนินการ (Confirmed Strategy):**
  1. **ห้ามลบข้อมูลระหว่างจัดเรียง Shard (`Zero-Destructive Sync`):** ยกเลิกคำสั่ง `deleteField()` อัตโนมัติในกระบวนการจัดเรียง Shard เบื้องหลังทั้งหมด ลบข้อมูลได้เฉพาะเมื่อแอดมินกดยืนยันลบรายงานด้วยตนเองเท่านั้น
  2. **เพิ่มฐานข้อมูลสำรองในเครื่องระดับ `IndexedDB` (ความจุสูงระดับหลายร้อย MB):** นอกเหนือจาก Cloud Firestore และ `localStorage` ระบบจะบันทึกสำเนาข้อมูลทั้งหมดลงใน `IndexedDB` ของเบราว์เซอร์โดยอัตโนมัติ ซึ่งไม่ติดเพดาน 5MB ทำให้ต่อให้โควตา Cloud Firestore เต็มระหว่างวัน เมื่อเปิดหน้าเว็บใหม่ข้อมูลก็จะยังคงอยู่ครบ 100% เสมอ
  3. **ปรับปรุงตัวกรองวันที่และแถบแจ้งเตือนข้อมูลย้อนหลังบนหน้าแดชบอร์ด:** แสดงจำนวนรายงานของวันนี้เทียบกับจำนวนรายงานสะสมทั้งหมดอย่างชัดเจน พร้อมปุ่มสลับดูข้อมูลเมื่อวานหรือภาพรวมทั้งหมดในคลิกเดียว

## 1. Overview & Core Concept

- **What It Does:** ป้องกันการสูญหายของข้อมูลรายงานผลการปฏิบัติงาน (DOE Work Permit Reports) ในทุกสถานการณ์ ไม่ว่าจะเกิดจากการเปิดหน้าเว็บทิ้งไว้ การเปิดใช้งานพร้อมกันหลายอุปกรณ์ หรือกรณีโควตาการอ่านข้อมูลรายวันของ Cloud Firestore เต็ม
- **Target Audience / Persona:** เจ้าหน้าที่กรมการจัดหางาน สำนักงานจัดหางานจังหวัด/กรุงเทพมหานคร ศูนย์บริการ และผู้บริหารส่วนกลางที่ติดตามผลการดำเนินงานตลอดทั้งวัน
- **Key Value:** ข้อมูลที่บันทึกแล้วจะคงอยู่ถาวร 100% ไม่ลดลงเมื่อรีเฟรชหรือเปิดใหม่ระหว่างวัน พร้อมกู้คืนข้อมูลที่ตกหล่นจากทุกแหล่งเก็บข้อมูลกลับมาให้อัตโนมัติทันทีที่เปิดระบบ

## 2. User Experience & Visual Design

- **Key User Flows:**
  1. **การเปิดใช้งานระหว่างวัน / เช้าวันใหม่:** ระบบโหลดข้อมูลจาก `IndexedDB` + `localStorage` + `Cloud Firestore (24 Shards & Single Reports)` มาผสานกันโดยยึดฉบับที่มีเวลาอัปเดตล่าสุด (`pickNewerReport`) โดยไม่มีคำสั่งลบข้อมูลเบื้องหลัง
  2. **แถบสถานะความครบถ้วนของข้อมูลบนหน้าแดชบอร์ด:** หากวันที่ปัจจุบันเพิ่งมีรายงานเข้ามาไม่กี่แห่ง ระบบจะแสดงแถบแจ้งเตือนชัดเจนว่า *"กำลังแสดงข้อมูลประจำวันนี้ (X รายการ) — มีข้อมูลสะสมทั้งหมด Y รายการ (คลิกเพื่อดูข้อมูลเมื่อวาน / ภาพรวมทั้งหมด)"* เพื่อไม่ให้ผู้ใช้เข้าใจผิดว่าข้อมูลหาย
  3. **สถานะการซิงก์และสำรองข้อมูล (Cloud & Local IndexedDB Badge):** แสดงสถานะการเชื่อมต่อฐานข้อมูลที่ส่วนหัวเว็บอย่างชัดเจนและโปร่งใส
- **Visual Identity & Theme:**
  - *Aesthetic Direction:* รูปแบบทางการของกรมการจัดหางาน (Official DOE Executive Dashboard) เน้นความชัดเจน อ่านง่าย และน่าเชื่อถือ
  - *Color Palette & Mood:* โทนสีน้ำเงิน-ครามราชการ (`indigo-950`, `blue-700`), สีเขียวมรกตยืนยันความสำเร็จ (`emerald-600`), และสีอำพันสำหรับแถบแจ้งเตือนตัวกรองวันที่ (`amber-500`)
  - *Typography & Hierarchy:* ฟอนต์มาตรฐานราชการไทย อ่านตัวเลขสถิติและวันที่ภาษาไทยได้ชัดเจน
- **Interactive Feedback & Motion:**
  - แถบสลับดูข้อมูล *"วันนี้"* / *"เมื่อวาน"* / *"สะสมทั้งหมด"* ตอบสนองทันทีโดยไม่ต้องโหลดหน้าใหม่
  - ระบบแจ้งเตือน (Toast Notification) ยืนยันเมื่อกู้คืนหรือผสานข้อมูลสำเร็จ

## 3. Key Product Decisions & Trade-Offs

- **Decision 1: ยกเลิกการสั่ง `deleteField()` อัตโนมัติใน Background Migration (`Zero-Destructive Shard Sync`)**
  - *Chosen Approach:* เก็บข้อมูลทุกคีย์ใน `report_bundles` ไว้ใน `liveBundleShardsCache` และ `bundleMap` เสมอ ไม่ว่าจะถูกบันทึกไว้ในหมายเลข Shard ใด และห้ามรันคำสั่ง `deleteField()` ลบคีย์อัตโนมัติในเบื้องหลัง
  - *Why:* ป้องกันปัญหาข้อมูลหายเมื่อเปิดเว็บหลายแท็บ หรือเมื่อการเขียนลง Shard ใหม่ติดโควตาชั่วคราว
  - *Alternatives Considered:* การย้าย Shard แล้วลบคีย์เดิมทิ้งทันที ซึ่งมีความเสี่ยงสูงที่จะทำให้ข้อมูลสูญหายหากเน็ตตัดหรือโควตาเต็มระหว่างย้าย
- **Decision 2: เพิ่มชั้นเก็บข้อมูล `IndexedDB` คู่ขนานกับ `Cloud Firestore` และ `localStorage`**
  - *Chosen Approach:* สร้างโมดูลจัดเก็บข้อมูลสำรองใน `IndexedDB` (รองรับข้อมูลได้มากกว่า 250MB+) คู่ขนานไปกับ `localStorage` (ที่บีบอัดให้เหลือเฉพาะชุดหลักชุดเดียวไม่ให้เกิน 5MB)
  - *Why:* แก้ปัญหาเพดาน 5MB ของ `localStorage` ได้อย่างเด็ดขาด ทำให้แม้ในช่วงบ่ายที่โควตาอ่านฟรีของ Cloud Firestore เต็ม การปิดแล้วเปิดเบราว์เซอร์ใหม่ก็จะโหลดข้อมูลจาก `IndexedDB` ขึ้นมาแสดงได้ครบทุกฉบับ 100%
  - *Alternatives Considered:* ใช้เฉพาะ `localStorage` อย่างเดียว ซึ่งเสี่ยงต่อการเกิด `QuotaExceededError` เมื่อมีรายงานสะสมหลายร้อยฉบับ

- **Data Model & State:**
  - `report_bundles/bundle_shard_0..23`: เก็บแผนที่รายงาน (`reportsMap`) โดยใช้ `{ merge: true }` เสมอ และอ่านข้อมูลทุกคีย์จากทุกเอกสารโดยไม่ตัดคีย์ที่อยู่ต่างหมายเลข Shard ทิ้ง
  - `reports/{reportId}`: เอกสารสำรองรายฉบับบน Cloud Firestore
  - `IndexedDB (doe_work_permit_idb_v1)`: ฐานข้อมูลในเบราว์เซอร์ที่เก็บ `DOEReport[]` ทั้งหมดโดยไม่ติดข้อจำกัด 5MB ของ `localStorage`
- **Interactive Component & State Mapping:**
  - เมื่อเปิดหน้าเว็บ ระบบจะโหลดข้อมูลเริ่มต้นจากทั้ง `localStorage` และ `IndexedDB` มารวมกันทันที จากนั้นเมื่อ `subscribeReports` ดึงข้อมูลจาก Cloud Firestore สำเร็จ ระบบจะผสานข้อมูลทั้งหมดเข้าด้วยกัน (`Smart Merge`) แล้วบันทึกสำรองกลับลง `IndexedDB`
  - บนหน้า `DashboardView` หากผู้ใช้ดูข้อมูลรายวันของ "วันนี้" ซึ่งมีจำนวนรายงานน้อยกว่าวันก่อนหน้า ระบบจะแสดงปุ่มลัดให้สลับไปดูข้อมูลของวันที่มีรายงานล่าสุดหรือภาพรวมสะสมทั้งหมดได้ทันที
